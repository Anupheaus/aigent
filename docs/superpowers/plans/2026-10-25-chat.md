# Chat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox syntax.

**Goal:** `agent.chat()`: stateful, streaming, persistent conversations with a UI-ready conversation model (snapshot + gapless patch stream + reducer + store), activity updates shared with tasks, `ask_user`, busy-time delivery (queue/steer/interrupt), threads, forks/branches, edit/regenerate, attachments, pinning, reactions.

**Architecture:** The existing turn loop (`run-turn`/`run-task`) is generalised into a reusable "run one agent turn over a message history" function; `task()` and chat turns both call it. A pure conversation module owns message/patch types, `reduceConversation`, and the store; the chat engine appends patches through one function so snapshot and stream cannot diverge. Sessions persist through the keyed write queue.

**Tech Stack:** TypeScript strict ESM, zod, vitest, fast-check. Nothing new to install.

**Spec:** master plan sections "Chat capabilities", "UI-ready conversation model", "Activity updates", "Rendering the agent's work in a UI", "User messages while the agent is busy", "Stopping tasks (and chat turns)" in `C:\Users\email\.claude\plans\i-want-to-create-hazy-church.md`; earlier slice plans/fix reports for conventions.

## Global Constraints

Same as the foundation plan's Global Constraints (functional, no classes, named exports, max 2 params, no `any`, `.js` suffixes, named constants, co-located `*.tests.ts`, barrels only, commit trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`), plus: no network; clocks/ids injected; the conversation snapshot and every patch are plain JSON (round-trip `JSON.stringify`/`parse` unchanged); `seq` is gapless and monotonic per session; applying the patch stream with `reduceConversation` from an empty state always equals `conversation()`; edit/regenerate/fork never delete history; sessions of one agent never see each other's messages; history stays private per session.

## Review Focus

1. Race tests: a user message arriving mid-stream, mid-tool, exactly at turn end, during `ask_user`, and while queued messages are being coalesced must neither be lost, duplicated, nor reordered.
2. `interrupt` leaves a consistent history: partial agent message kept as `cancelled`, completed tool results kept, no orphaned tool call without a result (provider-valid), side-effecting tools finish unless `force`.
3. Reconnect: `subscribe({ fromSeq })` returns exactly the missed patches; a reducer fed any prefix of the stream yields a valid state; streaming deltas assemble to the final text.
4. Branch integrity: edit/regenerate/fork produce independent branches; the active branch's history (what the model sees) contains only that branch's lineage; thread context contains only root + thread replies + a short main summary.
5. Persistence: a chat reopened from the store by `sessionId` reproduces the identical conversation snapshot; concurrent turns in different sessions do not interfere; `persistence: 'memory'` writes nothing to the store.

### Task 2: ask_user and question flow

**Interfaces (binding):** tool `ask_user` (strict, batch, `deterministic:false, cache:false`): `{ questions: [{ id (1..40, unique), text (1..500), type: 'text'|'single_choice'|'multi_choice'|'confirm'|'number', options?: [{ value, label }] (required for choice types, 2..20), default?, required: boolean, min?, max? }] }` min 1 max 10. Flow in chat: emits `question-opened` patches + `question` messages (`kind: 'question'`, non-compactable), sets status `waiting_for_user`, the turn **suspends** (no model request, no tokens); `chat.answer(questionId, value)` validates per type/constraints (precise per-question results; invalid ⇒ stays open and returns the error), `question-answered` patch + `answer` message (non-compactable) linked both ways (`questionMeta`, `answeredQuestionId`); when all required questions of the batch are answered the tool result envelope (per-question `{ id, ok, value }`) is returned to the model and the turn resumes; a normal `send()` reply while exactly one question is open answers it (documented rule), otherwise it is a new message. `unattended` ⇒ tool not registered and any call ⇒ `denied` envelope; the `onAmbiguity` policy applies. Stop/cancel while waiting works; pending questions survive `close()` + reopen by `sessionId` (persisted) and answering after reopen resumes the turn only if the turn state is checkpointed — **ruling: after reopen the question is still open and answerable, but resuming the suspended model turn is done by starting a fresh turn that includes the answered question (full checkpoint/resume arrives in the resume slice)**. Task mode: with `onQuestion` supplied, `ask_user` is registered and calls the callback; without it the tool is not registered.

### Task 3: Busy-time delivery, stop modes for turns, threads, branches

**Files:**
- Create: `src/chat/message-queue.ts`, `src/chat/delivery.ts`, `src/chat/threads.ts`, `src/chat/branches.ts`, `src/chat/steer-inbox.ts`
- Modify: `src/chat/chat-engine.ts`, `src/core/run-agent-turns.ts` (steer inbox consulted at safe boundaries; graceful/immediate stop already exist), `src/core/run-task.ts` + `agent-types.ts` (`TaskRun.steer(text)`), README
- Test: beside + race tests with FakeProvider delays

**Interfaces (binding):**
- `send(input, { delivery?: 'queue'|'steer'|'interrupt'; force?: boolean; coalesce?: boolean })`; default from chat `whileBusy`. **queue**: appended to `queue` (patch `queue-updated`), runs after the current work as its own turn; adjacent queued messages coalesce into one turn when `coalesce` (per chat default false); `chat.queue()` list, `queue.edit(id, text)`, `queue.move(id, toIndex)`, `queue.remove(id)` before start (precise errors after start). **steer**: delivered at the next safe boundary inside the running turn (after in-flight tool results return, before the next model request) via the steer inbox as an extra `user` message with `delivery.steered = true`, no extra model call; if the turn ends first it becomes a queued message. **interrupt**: aborts generation immediately; partial agent message kept `state: 'cancelled'` with `message-interrupted` patch; in-flight read-only tools aborted; side-effecting tools finish unless `force: true`; completed tool results kept; **history repair**: any assistant tool call without a result gets a synthetic `aborted` result so the next request is provider-valid; then the new message starts a fresh turn. `turn.stop({ mode: 'graceful' | 'immediate' })` / `turn.cancel()` as for tasks (graceful finishes the unit of work and ends `stopped`); `onStop: 'discard' | 'keep'` for queued/steering messages (default keep for chat). `task.steer(text)` delivers like chat steer.
- **Threads**: `send(text, { replyTo })` opens/continues a thread on that message; the thread turn's model context = root message + thread replies + one short summary of the main conversation (a deterministic extract of the last N=6 main messages' text, truncated; no model call) — asserted smaller than full history; `chat.thread(messageId)`; `thread.promote()` appends a summary message (kind `summary`) to the main line.
- **Branches/forks**: every message has a `branchId`; `chat.edit(messageId, newText)` and `chat.regenerate(messageId)` create a new branch from that point (old branch intact and selectable via `chat.selectBranch(branchId)`, patch `branch-selected`); `chat.fork({ atMessageId? })` returns a new `Chat` session (new `sessionId`, `parentSessionId` + `forkPoint` recorded, history copied by reference up to the point) that evolves independently; `chat.branches()` returns the tree. Model-visible history = the active branch's lineage only.
- **Attachments & pinning & reactions** (also this task): `send({ text, attachments })`: images require `provider.capabilities.vision` (else `invalid_input` with a clear message, or text-description fallback when `attachments.onNoVision: 'describe'` supplies a describer callback); files are read through an injected `readAttachment(ref) => Promise<{ name; mimeType; bytes }>` hook (no filesystem access in core; the fs-policy slice supplies it), stored by content hash in collection `attachments`, inlined if ≤ 8 KiB text else referenced by handle with a one-line summary; `chat.pin(messageId)` sets `pinned` and `compactable:false`; `chat.react(messageId, 'up'|'down', comment?)` ⇒ `ai.feedback` against that message's `responseId` (correct/incorrect) and `userRating` meta; `title` generation: optional `autoTitle: true` makes one cheap call after the first exchange (provider call counted separately in usage; off by default).
